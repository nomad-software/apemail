# ApeMail an email client.

ApeMail is for Linux only: there is no support for macOS or Windows, in the code, the packaging or the workflows, and none is to be added.

## IMPORTANT

I am going to be testing this on live mailboxes! Under no circumstance should you preform a destructive operation without a confirmation!!!!!!!!!

How the code keeps to this (keep it that way):

* There is no read-only mode: changes to mailboxes are always allowed (the user tests on a mailbox kept for the purpose). The confirmations and expunge safeguards below still apply.
* Synchronising never changes anything: folders are opened with `EXAMINE`, never `SELECT`, and the sync and idle connections are never writable. Only the connection that does what the user asks can change a mailbox.
* Messages are downloaded with `BODY.PEEK[]`, so downloading does not mark them read. A message is marked `\Seen` when it is shown.
* Deleted mail always goes to the trash folder on the server, without a confirmation, as nothing is lost (the trash is made if the mailbox has none). **The only confirmation is for a permanent delete**: do not add confirmations for anything else that deletes or moves mail.
* Deleting from the trash asks for confirmation and, if accepted, deletes for good: `engine.Delete` refuses any folder but the trash.
* Deleting a folder (Delete Folder… on its menu in the side bar) is the other permanent delete. It asks for confirmation, showing the folder and those within it with how many messages each holds (`engine.FolderContents`, by LIST and STATUS on the op connection), and, if accepted, deletes them deepest first (`engine.DeleteFolder`, `remote.Conn.DeleteFolder`). Just before deleting it lists and counts them again, and deletes nothing if anything differs from what the user was shown (count, UIDNEXT, UIDVALIDITY, or the folders within), as mail arriving meanwhile. It holds each folder's `folderSyncs` lock, so it refuses a folder being synchronised and none is synchronised while it is deleted. The inbox, the folders the account uses (Sent, Drafts, Trash, Archive) and any folder holding one are never deleted (`engine.Deletable`, which also greys the menu item out). The connection leaves the folder it has open by `EXAMINE INBOX`, never by `CLOSE`, which expunges. The local copy of a folder deleted is thrown away (`forgetFolder`).
* Expunging is only ever by UID (`UID EXPUNGE`, UIDPLUS). A server without UIDPLUS is never asked to expunge, and one with neither MOVE nor UIDPLUS is not asked to move, because a plain `EXPUNGE` would also remove messages another client marked `\Deleted`. go-imap's `Move` falls back to a plain `EXPUNGE` on such servers, so `remote.Conn.Move` checks before calling it.
* Messages are only ever asked for by UID (`UID FETCH`, `allUIDs`), never by sequence number. While another client's expunge has yet to be reported, a server can answer a `FETCH 1:*` by number with nothing at all (go-imap's in-memory server does), and a sync took every message of the folder for gone; and numbers change as messages go, so the answer for one can be taken for another's. `TestSyncWhileAnotherExpunges` holds a sync just before it fetches while another client moves a message away.
* `\Deleted` can only be set by `remote.Conn.Delete`, which then expunges just those UIDs.
* Every operation on UIDs checks that the folder's UIDVALIDITY on the server still matches the one the UIDs were listed with, so stale UIDs never hit other messages. That UIDVALIDITY is given with the UIDs by whoever asks (`engine.Message`, `SetFlag`, `Move`, `Archive`, `Trash`, `Delete` take it; the UI gives `messageList.uidValidity` as it was when the messages were selected, the view's `validity`, a drag's `UIDValidity`), never read from the engine's index when the op runs: the folder may have been numbered anew between, as while the user is asked whether to delete for good (`TestStaleUIDsRefused`, `TestDeleteForGoodFromFolderAsked`). A list given an index numbered anew drops its selection (`TestRenumberedDeselects`).
* Old drafts that a compose window replaced are moved to the trash, without asking, when the window closes, as other clients do. The latest draft saved is kept unless the message was sent: closing with Discard throws away only what was written since (`TestDiscardKeepsSavedDraft`).
* Removing an account (Accounts menu only: not the account's menu in the side bar) deletes only the local files, after asking. The server is not touched.
* The local copy is a cache: wiping it, for example when UIDVALIDITY changes, is fine and is not a destructive operation.
* Tests in `internal/remote` and `internal/engine` run against go-imap's in-memory server (`internal/remote/remotetest`), record the commands sent (those that read or change messages, and those that make, delete, rename or close folders), and check that synchronising sends nothing that changes a mailbox. Keep them passing. `remotetest.Server.Hold` stops one client part way through (at a line it sends), so that a test can do something while, say, a sync is running. go-imap's in-memory server has no CONDSTORE, so `internal/remote/condstoretest` is a small IMAP server of our own that has (one folder, the inbox): tests add mail, set flags, expunge, renumber the folder, turn the counting of changes off (`NoModSeq`) or start it again lower (`ForgetChanges`), have it write structures the client cannot read (`BadStructures`), and see the commands sent.

## Testing

This app handles people's email, which is incredibly important and must be handled in a safe and professional way. Test coverage should be as high as possible.

* Every change comes with tests, and every bug fix comes with a test that fails without the fix.
* Anything that touches a mailbox (moving, deleting, flagging, appending, sending, synchronising) is tested against the in-memory server (`internal/remote/remotetest`), and sending against the SMTP server for tests (`internal/send/sendtest`). The test checks both what the client does and what is on the server afterwards, including that other messages are left alone.
* Destructive paths are tested both ways: that they happen when confirmed, and that nothing happens when the user declines or the precondition fails (wrong folder, stale UIDVALIDITY, missing UIDPLUS, no trash folder).
* Encryption is tested so that nothing is written to disk in plain text: accounts, passwords, indexes, messages, the outbox, the address book.
* The UI is tested offscreen (`internal/ui`, `QT_QPA_PLATFORM=offscreen`), with confirmations answered by replacing `confirm`. Warnings go through `warning`, which the tests replace too, so that one is never left in a dialog no one closes: a wait that times out says what the program warned of. Show every warning through it, never `QMessageBoxWarning` itself. The same goes for what the user is only told (`information`) and for the question about saving what is written (`askSave`, answered in tests with `answerSave`): no `QMessageBox` is opened but through one of the four. A test touches widgets on the UI's thread through `qutetest.Run(t, ...)`, in which `t.Fatal` works and a panic fails the test (`qute.PostSync` where there is no test to fail, in which neither does); `onUI` returns a value from there. Keys and clicks are sent as the user makes them: made with `qtgui.NewQKeyEvent` and `NewQMouseEvent` and sent with `QCoreApplicationSendEvent` (`moveMouse`, `dragBorder`), or by `qutetest.Key`, `Type` and `ClickAt`.
* Every test run has a timeout, so that a hang fails with the stacks of what was waiting rather than waiting for ever: `make test` runs `go test -race -timeout 5m ./...`, and a test that waits on the engine or the UI waits with a deadline (`recv`, `result` and `wait` in the tests). Never run the tests without `-timeout`.
* Run `make test` before considering work done, and check coverage with `go test -cover -timeout 5m ./...`.

## Code quality

The code base must stay clean, maintainable and readable. Whenever something is changed, deal with the technical debt and cruft around it as part of the change, rather than leaving it for later:

* Remove code that is no longer used (`go run golang.org/x/tools/cmd/deadcode@latest ./...` finds it; only test helpers should be reported), wrappers that add nothing, parameters that are not used, and comments or error messages that no longer say what the code does.
* Keep one thing in one place: a helper rather than a pattern repeated, and a file for each part (as `accountdialog.go`, `settingsdialog.go`, `dialog.go`).
* Match the style around it: comments in full sentences saying why, names that say what things are, `gofmt`, and `go vet` clean.

## Premise

* This is to be a simple email client that is imap based at the start.
* It will be written in Go.
* The UI will be simple and use the qute library (Qt 6, `github.com/nomad-software/qute`, which needs Qt 6.12 or later).
* Settings, accounts and email storage are encrypted using ssh keys and the age library: https://github.com/FiloSottile/age, similar to how triggerapi was done (`internal/crypt` is adapted from it, but writes binary age rather than armoured, as armour makes mail a third bigger).
    * The client settings are a separate JSON file, **not encrypted**, as it names the keys (`~/.config/apemail/settings.json`).
    * Each account is a separate encrypted JSON file, **including its passwords** (`~/.local/share/apemail/accounts/<id>.json`).
    * The folder the accounts and their mail are kept in is a setting (File > Settings, `dataDir`). Changing it moves everything there, after asking; the new folder must be empty or not exist. The settings file itself stays in `~/.config/apemail/`, as it is read before anything else.
    * The window's size (and whether it is maximised), the sidebar width, the message list height, the widths of the From (or To) and Date columns of the message list (one pair for every folder, not one for each), and which accounts and folders of the side bar are open or closed are kept in the settings when the window closes, and restored when it opens. The open folders are kept by a hash of their names (`settings.FolderKey`), as the settings are not encrypted and must not name folders. The tree keeps them as they were when the folders are listed again.
    * The size of the compose window is kept in the settings (`composeWidth`, `composeHeight`) when one closes, unless it is maximised, and the next one opens at that size.
    * The mail of an account is kept in a folder of its own beside that (`accounts/<id>/`):
        * `folders.json`: the list of mail folders.
        * One folder per mail folder, named by a hash of the folder's name so names are not visible without the keys (`f-<hash>/`).
            * `index.json`: an index of the headers (summaries) of the folder's messages, which is all the message list needs, and the server's count of changes to the folder (`highestModSeq`, CONDSTORE). It is compact JSON compressed with gzip and then encrypted (`jsonfile.SaveCompressed`; `jsonfile.LoadWith` reads it, and the older uncompressed ones), as that of a folder of 100,000 messages is 44 MB uncompressed. This replaced "one JSON file per message", which would mean decrypting thousands of files to list a folder.
            * `<uid>.eml`: each message that has been downloaded, as the raw RFC 822 the server sent (not JSON, which would base64 the attachments again).
        * `outbox/`: mail to send and drafts to save that could not be, for want of a connection.
    * `addressbook/contacts.json`, beside the accounts (a file of its own there would be taken for an account): the address book, the name and address of each contact (`internal/addressbook`), one for all the accounts. It is read and saved off the UI thread (`internal/ui/addressbook.go`), and is nil until read, so that one which cannot be read is never saved over; saves are waited for before the files are moved or encrypted again, and when the window closes.
    * Nothing is loaded or saved without keys.
* Performance: all network work, encryption and decryption happen off the UI thread. Each account has an engine (`internal/engine`) with three goroutines, each with its own IMAP connection: one synchronises, one does what the user asks (open, move, flag, append), so it is not held up by a long sync, and one idles in the inbox. Synchronise All Folders and Update Unread Counts each run on a connection of their own while they last, so that Get Mail is not held up behind them. A folder is never synchronised on two connections at once (`folderSyncs`): a sync that finds its folder being synchronised already leaves it to that one. What each part of the engine is doing is shown together in the status bar (`say`, by `statusPart`). Results are posted to the UI thread with `qute.Post`. The message list is a virtual model (`QAbstractTableModel`), so a big folder is shown at once.
    * Every goroutine of an engine is started with `spawn`, which `Close` waits for, and none is once it is closed (`stop` is closed with `mu` held), so nothing touches the local copy after `Close` returns, when it may be moved. What was asked of the op worker (`do`, a queue `mu` guards) and had not started when it closes is given no connection, as when the server cannot be reached, so every caller hears back and a draft goes to the outbox.
    * What is posted to the UI about the same thing is posted with the lock it changed under held (`changed`, `Open`, `listed`, `addFolder` with `mu`; `say` with `statusMu`), so it arrives in the order it changed: the last a listener hears is how things are.
    * A sync that fails on a connection kept from before is tried once more on a new one, as the server may have dropped it (a restart, a router overnight); the watcher connects again (`watchRetry`) and has the inbox checked when it does. What the user asks cannot always be asked twice (an append would be made twice), so the op worker instead tries its connection first (`remote.Conn.Check`, a NOOP) when it has not been used for a minute (`opIdle`), and makes another if it does not answer (`TestOpAfterServerRestarted`). `remotetest.Server.Restart` drops every client, for the tests.
    * A message downloaded is kept only if its folder is numbered as it was when it was asked for (`keepMessage`, with `saveMu`), as its UID may since be another's. The folders are saved and kept as one, with `saveMu` (`listed`, `addFolder`). Each piece of pending work has a file of its own (`store.AddPending`, `pendingMu`).
    * What the UI does away from its thread for a dialog answers through `inBackground`, which drops the answer once the dialog has been deleted, with the widgets it would use. A compose window does not close while it is sending or saving a draft (`sending`, `savingDraft`), as the answer is shown in it: from when its body is asked what it holds, which it answers on a later turn of the event loop (`TestCloseWhileBodyAnswers`).
    * The concurrency tests are `internal/engine/concurrency_test.go` and `internal/ui/concurrency_test.go`; keep every new goroutine, lock and post covered there, with a test that fails without what it guards.
    * A mailbox can hold many years of mail, with folders of 100,000 messages; `internal/store` and `internal/ui` have tests and benchmarks at that size (`make bench`). Keep them in mind:
        * A change to an index is shown at once but saved a little later (`saveDelay`, two seconds) by the engine's saver goroutine, from a copy and outside the lock, several folders at once, and whatever is left when the engine is closed. `saveMu` (taken before `mu`) is held while indexes are saved and while a folder's local copy is thrown away, so that no index is saved into a folder after it was. Close an engine before deleting or moving its files.
        * A sync that finds nothing new saves and shows nothing. With CONDSTORE (RFC 7162) a sync asks only for what has changed since the count of changes the index was made at (`FETCH ... (CHANGEDSINCE n)`), and nothing at all if the count and the number of messages are as they were; messages that have gone, which need not change the count, are looked for (`UID SEARCH`) only when the number of messages says some have. A server without it, a folder it does not count (NOMODSEQ), one numbered anew, or a count lower than the index's, is synchronised whole.
        * The index of a folder is read from disk outside the engine's lock the first time it is opened (`preload`).
        * The message list works out what each row is sorted by once (on every processor for a large folder), and when only flags have changed, which is most changes, updates those rows in place rather than sorting again (`messageList.update`). It keeps the row of each UID.
* qute tracks who owns each Qt object, and frees what Go owns and no longer refers to, so nothing is kept alive or deleted by hand for the bindings' sake: no `runtime.KeepAlive`, and no `Delete` of a value once Qt has copied it. What the code keeps to:
    * A class whose virtual functions Go overrides is a struct that embeds the class's `Base` type (`qtwidgets.QTreeViewBase`), defines the functions as methods (`StartDrag`, calling `Super()` for Qt's own), and is made with the class's `With` constructor (`qtwidgets.NewQTreeViewWith(l, nil)`): `Window`, `composer`, `messageView`, `messageList` and its `listModel` and `listHeader`, `folderTree`, `flowLayout`, `iconEngine`, `themeStyle`, `filterField`, `resizingScroll`, and `hostPage` and `hostView` of a web page. An exported method of such a struct with the name of a virtual function is taken for an override, so name others otherwise.
    * A widget or action is given its parent when it is made, or is put in a layout or a widget straight after, so that it goes with its window. One with a handler and no parent is never freed (`qute vet` reports them: build `cmd/qute` in qute's folder and run `qute vet ./...` here, which should report nothing).
    * In a handler (a signal, an event, a function Qt calls) a `QObject` is deleted with `DeleteLater`, never `Delete`, which panics there. An event, painter or style option handed to a handler is gone when it returns: keep what is read from it, not the object.
    * Sizes, points, rectangles, margins and colours are plain Go structs (`qtcore.QSize`, `qtgui.QColor`); a colour written as `#rrggbb` is read with `parseColour`, and its lightness with `lightnessOf`.
    * A value the model's `Data` returns is copied by Qt before the override returns, so those made once (`boldValue`, `noValue`) are returned as they are. `TestListWhileCollecting` and `TestIconsWhileCollecting` draw while the collector runs all the while.
    * The selection of a large folder is read a row at a time by `RowIntersectsSelection` (rows are selected whole, and it asks the model about one cell of the row where `IsRowSelected` asks about each; the answer is kept until the selection changes), rather than as a list of an index for each of 100,000 rows, and a drag is started by the list (`StartDrag`) rather than through the model's `mimeData`, which would be handed one for every cell (`TestLargeSelection`).
* Local folders: not supported. We are IMAP only and are a terminal for remote mailboxes. We only download mail and store it locally as a cache; really we are interacting with a remote mailbox. The exceptions are internal and not shown as folders: the **outbox** (mail sent while the SMTP server cannot be reached, sent on the next Get Mail), **drafts saved while offline** and **copies of sent mail that could not be put in the sent folder** (`engine.appendSent`; both appended on the next Get Mail).
    * Mail is sent once the SMTP server has taken it: an error from the goodbye after is not one of sending (`send.Send`, `TestSentThoughGoodbyeFails`), as it would have the user send it again. Mail that could be neither sent nor kept in the outbox is not said to be unreachable (`send.ErrUnreachable`), which the compose window takes for kept, and closes on (`TestNeitherSentNorKept`).
* One copy runs for each user (`internal/instance`, from `main.go` before Qt starts): it holds a lock (`flock` on `apemail.lock`, let go by the system if it dies) and listens on `apemail.sock` beside it, in `$XDG_RUNTIME_DIR` or a folder `apemail-<uid>` of the user's own (0700, checked) in the temporary folder. A copy started while it runs sends it the desktop's `XDG_ACTIVATION_TOKEN` and leaves; the one that runs puts the token in its environment, where Qt's Wayland support reads it, and raises the window (`Window.Activate`). Two copies never work on the same local copy at once. One that holds the lock but does not answer (`ErrNoAnswer`) keeps a new copy from starting; any other failure of the check is warned of and the program runs.

## Not wanted

* No polling every N minutes (a POP3 throwback). New mail comes from IMAP IDLE on the inbox while running, plus checking the inbox on start and Get Mail.
* No synchronising of folders that are not looked at, and no downloading of messages in the background: a mailbox can hold many years of mail. Get Mail (and "Get Mail" on a folder's menu) checks the folder that is selected, or the account's inbox if the account is, lists the folders again (one LIST, which looks inside none) and sends the outbox (`engine.Refresh`). Opening a folder synchronises it. A message is downloaded when it is opened.
* Two things the user asks for in the Accounts menu (and an account's menu in the side bar) look at every folder, and only when asked:
    * Update Unread Counts asks the server how many messages of each folder are unread (STATUS, every folder asked before any answer is waited for), which opens none and fetches nothing. The folder tree keeps the counts it is given (`folderTree.unread`), so that they stay when the folders are listed again and the tree is made again.
    * Synchronise All Folders (`engine.SyncAll`) fetches the headers of every folder, but no message: the inbox first, then the drafts and sent mail, the rest, and the trash last. While it runs the item says Stop Synchronising All Folders, which drops its connection at once (`StopSyncAll`, `ErrStopped`).
* No search, threaded conversations, unified inbox, templates or spam handling. These are what is wrong with other clients.
* OAuth2 is left out for now and can be added later (Gmail and Microsoft 365 need it).
* Kerberos and NTLM are left out for now.

## UI

* The UI is very familiar and simple: the desktop email clients of years ago.
* Menu bar: File, Message, Accounts, Help.
* Button bar: large buttons with text underneath (Get Mail, Write, Reply, Reply All, Forward, Archive, Address Book, Delete). Address Book has a separator each side.
* A letter, number or other character key is never a shortcut on its own, as it is too easily pressed by mistake; it needs a modifier (Ctrl, Alt...). Function keys and special keys (F5, Delete, Escape...) are fine on their own: Delete deletes (and removes an attachment in the compose window), F5 refreshes (Get Mail), and Escape closes the compose window (File > Close, asking about a message not sent, as its close button does). Standard shortcuts such as Ctrl+A for Select All are never taken over. Get Mail F5, Write Ctrl+N, Reply Ctrl+R, Reply All Ctrl+Shift+R, Forward Ctrl+L, Archive Ctrl+Shift+A, Delete Del, View Source Ctrl+U and Filter Ctrl+F (Message menu), Address Book Ctrl+Shift+B (File menu). A test checks this.
* File > Settings is Ctrl+, (the usual shortcut for preferences). It has tabs, as triggerapi's settings do: General (encryption, where the accounts are kept) and User interface (fonts, theme).
* Theme (`theme`: `light`, `dark`, or empty to follow the system; `internal/ui/theme.go`): light and dark are the Fusion style, which honours a palette on every desktop, with a palette of its own, through a proxy style (`newThemeStyle`) that edges the boxes of check boxes again half way between text and base, as Fusion's edge, a shade of the window, barely shows on either (`TestCheckBoxEdges`); following the system puts back the style the program started with and an empty palette, which is the desktop's and which Qt keeps up to date as the desktop changes. A change takes effect at once. Messages shown and written, HTML or text, follow the theme too: none is forced onto a white page. A message shown takes the theme's colours for its text and links where it gives none of its own (by a `:where` rule, which any of its own outweighs), and the theme's base behind it as the colour of the page (`SetBackgroundColor`), not in CSS, so that a background its body has, by style or `bgcolor`, still fills the page; not `color-scheme`, as Chromium paints a dark page its own colour. A change of theme loads the message again in a view that is seen, and in one that is not once it is (`messageView.stale`), as every view reloading at once is slow.
* Help > About shows the version beside the name (`appVersion`: what Go records from git when it builds, as plain major.minor.patch, the tag a build is or follows, or `dev` where there is none), and lists the licences of Qt (LGPLv3, with the notice it asks for) and of every library the program is built with, as triggerapi does. Keep it up to date when dependencies change: `TestAboutNamesEveryLibrary` fails for a module of `go.mod` it does not name.
* Side bar: each account, with its folders below it as a tree (Inbox, Drafts, Sent, Archive, Trash first, then the rest, nested by the server's delimiter). The folder for each use, the one the account chooses or else the one found (`engine.SpecialIn`, as the engine finds it), is shown by the name of the use (`Special.Name`: Archives as Archive), so that every account looks the same; its tool tip has the server's name, and the folders within it stay below it. Unread counts are shown.
* Messages pane: a paperclip for a message with attachments, subject, from (or recipient in Sent/Drafts) and date (the full date and time). Click a header to sort. The paperclip is `store.Summary.Attachments`, from the BODYSTRUCTURE of each message (`remote.hasAttachments`: a part marked as an attachment, or one that is not text and not within a `multipart/related`, whose parts the HTML shows). It is asked for apart from the headers and after them (`Conn.attachments`, into `Update.Attachments`): go-imap ends the connection on a structure it cannot read, which must not keep new mail from being listed, so that is told (`Update.AttachmentsErr`) and the rest of the sync stands (`TestUnreadableStructure`). An index saved before summaries had it (`store.Index.Attachments` false) has it looked up once by the next sync, for the messages it knows. The list draws a row whose paperclip changes again in place, or sorts again if sorted by it (`messageList.update`). Unread is bold. Above the list, the path of the folder as the side bar names it and the folders it is within, joined by / whatever the server's delimiter (`folderTree.folderPath`: Archive/2026 for Archives/2026 when Archives is the archive) and how many messages it has once they are listed (`Window.showFolderTitle`, called through `messageList.changed` whenever what is listed changes); nothing where no folder is listed.
    * Beside that title, taking half of the row they share (giving way to a title too long for its half), is a field, hidden until Message > Filter (Ctrl+F, `Window.openFilter`) shows it, that filters the list as it is typed in (`Window.makeFilter`, `messageList.setFilter`): only the messages with every word typed, in any order and whatever its case, each in their subject, From or To (`matchesFilter`), as TriggerAPI's search of requests does, never their bodies, so that it is quick. Ctrl+F goes to it. `all` holds every message of the folder, sorted, and `rows` those shown, so changing the filter sorts nothing. Rows are not hidden in the view (`SetRowHidden`): at 100,000 messages that took about 100 ms a key against 35 ms, and hidden rows can stay selected. A message filtered out has no row, so it cannot be selected and nothing done to a selection touches it (`TestFilterProtectsHidden`). The title then says how many of how many are shown. Escape, its clear button, choosing another folder or there being no folder closes it, emptied (`Window.closeFilter`). Delete in the field edits the text and never deletes mail (`TestFilterKeepsDeleteKey`).
    * The columns fill the list as those of other clients do: dragging the border between two columns trades width between them (the right edge of Date trades with Subject), and Subject takes what the window gains or loses. So Date is widened by the border on its left; a plain `QHeaderView` only resizes a column by its right edge, which for the last one is the side of the list. Columns cannot be moved. The From and Date widths are kept in the settings.
* Deleting (to the trash, or for good) or archiving selects the message after those that went, or the one before them if they were the last, once they have all gone from the list (`messageList.selectNextLater`, `next`), so that another press deletes it. Choosing other messages meanwhile, or the operation failing, forgets it.
* Listing the folders again keeps the folder selected without opening it again (`folderTree.setFolders` holds back `selected` while it makes the tree), so the list and the message shown stay; only a folder that has gone changes what is listed.
* Messages are moved between folders by dragging them from the list onto a folder in the side bar. They can only be dropped on a folder of the same account that can hold messages; the move is done on the server (MOVE, as in Move).
* Message pane: headers (From, Reply to, To, Cc, Date, and Attachments with how many there are, a row shown only for a message with some), attachments (click to save; a pane only as tall as its rows, so that the height to spare goes to the body, `TestAttachmentsPaneHeight`), and the body. The attachments wrap onto as many rows as they need (`flowLayout`, as Qt has no such layout), in a scroll area as tall as three rows at most (`attachRows`), so that a message with many never widens the window (`internal/ui/attachments.go`). Each is a flat button with no tool tip, shaded while the mouse is over it (`attachmentStyle`). Save All… (shown for more than one) saves them all in a folder chosen (`chooseFolder`; clicking one asks where through `chooseFile`; tests replace both) and never writes over a file there (`saveNew`, `O_EXCL`, as `name (2).pdf`).
    * Message > View Source (Ctrl+U) shows the message as the server has it, in a read-only `QPlainTextEdit` window of its own (`internal/ui/source.go`), so nothing in it is rendered or fetched. It is taken from the local copy (or fetched as opening does) and changes nothing. The window belongs to the main window, so it closes with it; Escape closes it. It is in the code font of the settings (File > Settings, User interface tab, "Code font": `codeFont`, `codeFontSize`, each empty for the system's monospaced font, which Default goes back to), which a change puts into effect in the windows open too. Any font can be chosen, not only monospaced ones.
    * HTML is shown by Qt WebEngine (Chromium within the program, `internal/ui/webview.go`), exactly as the message has it: nothing in it is rewritten, hidden or linked, for showing, replying, forwarding or sending (`Message.HTML`, `TestHTMLAsItIs`). Do not bring back fixes of HTML for a renderer. Only the policy it is shown with and the theme's colours go before it, after its doctype if it has one, so that it is laid out as it asks (`webPage`, `TestDoctypeFirst`). JavaScript is off, as is all else a page could reach out by (`webProfile`), in a profile of the program's own, off the record (`TestProfileOffTheRecord`), so nothing of it is written to disk. It is kept from the internet three ways, and keep all three:
        * It is served from memory by a scheme of the program's own, registered before the application is made (`PrepareWeb`): `apemail://p<id>-<serial>/message` (or `/edit` for the body of a message being written), the host naming the page (`webPages`, of `webHost`s: the view and each body) and what it shows, which changes with each (`serial`), so that nothing is served for a page shown before (`shownBy`); `cid:` parts by the same handler, for the page that asks (`serveWeb`, `webContent`).
        * Every request goes through the interceptor (`interceptWeb`, deciding by `webRequest`, which `TestRequests` checks): only the page of a message a view shows (whatever the first party says, as it is the page before while that is still loading, which once left the pane blank), what that page asks of its own host, `cid:` and `data:`. Images on the web it asks for (any of type image, backgrounds too) are refused and remembered (`want`), and once fetched are served in their place by a redirect to the program's scheme. Navigation goes only to the message shown and places within it; a link clicked, or one for a new window, is followed outside (`navigate`, `follow`), and a form is not sent.
        * Chromium has no network at all: its flags (`webFlags`, after any the user gives in `QTWEBENGINE_CHROMIUM_FLAGS`) send every connection to a proxy on the closed discard port, loopback included, as `<link rel="preconnect">` made one past the interceptor. They also turn the graphics card off (`--disable-gpu`): mail needs none, nothing a message holds reaches its driver, and the drivers that blank a page or cannot share frames with Qt (GBM, which Qt WebEngine warns of) are not used. Do not make it a setting (`TestChromiumFlags`). `TestNothingFetched` shows a message that names a local server in every way a page can, and fails if a connection is made to it.
        * The view's tests wait for its page to load (`showWhole`, `loadedWhole`) and read its text by selecting it (`pageText`), which only a page with the focus does. A page that is not seen is not drawn and asks for no images, so a test of either shows its window.
    * Load Remote Images, a button at the bottom right of the message's header shown once the page has asked for images on the web (`messageView.want`), or the account's setting `loadRemoteImages` (off by default; Composition & Sync tab), loads them (with the setting the button is hidden while they load, and shown only if some could not be loaded, to try them again): `internal/images` fetches them away from the UI's thread (no cookies, no referrer, redirects only to the web, at most 100 images, 10 MB each, six at once, 30 seconds each), keeps only responses that are images, and the page is loaded again to be given them. Once allowed, those the page asks for later are fetched too, each once (`tried`). Showing another message cancels the fetch (`forgetImages`), and what arrives for a message no longer shown, or once the view is destroyed (`gone`), is dropped. Links open in the browser (`openURL`, which tests replace); `mailto:` opens a new message (`TestLinksOpen` clicks them). The body's menu has Open Link and Copy Link Address on a link, Copy and Select All (`contextMenu`). Showing a message leaves the focus where it was, as in the list, where Delete deletes.
* Address book (`internal/ui/addressbookdialog.go`): a window of its own, belonging to the main window, listing the contacts as the messages are listed (no grid; click a header to sort by name or address, the rows sorted in `bookWindow.sorted` so they stay in the order of `contacts`), with New, Edit, Remove (which asks, as it cannot be undone) and Write. Double-clicking a contact closes it and opens a compose window to them. Each address is in it once, whatever its case (`addressbook.Book.Add` checks, and only gives a name to one that had none). The message pane has a button that adds whoever replies go to, as replying does: the Reply-To addresses if the message has them (the button is then beside Reply to), or else the sender (beside From). It is enabled only while they are not in the book. Sending a reply (a message with `In-Reply-To`) adds its To addresses.
* Compose window: From (account), To/Cc/Bcc, Subject, attachments, plain text or HTML (bold/italic/underline, bulleted and numbered lists, images). Send, Save Draft, Attach. Double-click a message in Drafts to continue it.
    * The body is a page of Qt WebEngine, as messages are shown in, that can be edited (`internal/ui/editor.go`, `bodyEditor`): `contenteditable`, or `plaintext-only` for text, served from memory as the view's pages are (`webPage`, `webHost`), in the same profile, with the same interceptor and policy, so that a message quoted runs no scripts and loads nothing from the internet (`TestQuoteKeptOffline`), and a reply to a newsletter opens at once (`TestReplyQuickly`). Its images on the web follow the account as the view's do: a reply, forward or draft of the message shown starts with those the view has loaded (`composer.addWebImages`), and if the account loads images when a message is shown, the body fetches the others it asks for (`bodyEditor.webImage`, `fetchImages`, by `internal/images`), and has only those asked for again (`retry`), as loading the page again would lose what is written. What is written is kept `bodyRoom` pixels from the edges by the body's padding (`:root > body`, important, which outweighs a newsletter's `body` rule), as a newsletter quoted takes the margins of the body away, and its style applies to the whole body. The padding is within the body's width (`box-sizing: border-box`), as newsletters make the page and body 100% wide, which room outside them, as a margin or the page's padding, makes wider than the window, to scroll from side to side (`TestRoomAroundBody`). Qt's own rich text (`QTextEdit`) is used nowhere: do not bring it back. The program's script (`editorScript`) runs in the ApplicationWorld, which runs though JavaScript is off and which the page cannot reach: Go calls it (`bodyEditor.call`, waiting in `pending` until the page has loaded) and it answers in the console, which only it can write to (`consoleMark`), with what the body holds (`content`, asked by a number), that something was typed (`modified`) and the format at the cursor (`onState`, which the buttons show). What the body holds is only had that way, so `composer.draft` takes a function, and Send and Save Draft go on once the body has answered. Formatting is the editing commands (`exec`: `bold`, `insertUnorderedList`, `insertHTML` for a picture); the Edit menu the page's actions. The window whose field or body takes the focus has the Edit menu act on it, by one watch of where the focus goes (`watchFocus`), as the body's widget is Qt WebEngine's. A change of theme changes the colours of the page in place, as loading it again would lose what is written.
    * To, Cc and Bcc complete the address the cursor is in from the address book (`addresscomplete.go`): any part of a name or address matches, and the others in the field are left as they are. Commas within quotes do not separate addresses, and `message.FormatAddress` quotes a name that has one, so that the field is read back as it was.
    * Menus: File (Close, whose shortcut is Escape), Edit (Undo, Redo, Cut, Copy, Paste, Paste Without Formatting in HTML, Delete, Select All), Format (in HTML: the formatting buttons' own actions, so both show the same state) and Options (Return Receipt, Delivery Status Notification). Edit acts on the field or body last in focus (`watchFocus`); the body's own menu has the same items. Its items only show the standard keys (after a tab in their text), as the fields and body take those keys themselves; as real shortcuts they would also fire while the attachment list has the focus.
    * Return Receipt sets `Disposition-Notification-To` to the sender (RFC 8098), and is read back from a draft. Delivery Status Notification asks the SMTP server for DSN (RFC 3461: `RET=HDRS`, `NOTIFY=SUCCESS,FAILURE`); go-smtp leaves it out for a server without DSN, which sends as usual. Mail waiting in the outbox keeps the request.
* Return receipts asked for (`internal/ui/receipt.go`): showing a message with `Disposition-Notification-To` asks, through `confirm`, whether to send the receipt, unless the message has `$MDNSent` (RFC 3503) or is in the sent or drafts folder. The answer, yes or no, sets `$MDNSent` on the server, so the user is asked once, here or in another client; a receipt that could not be sent (but not one put in the outbox) leaves it unset, to be asked again. The receipt is an RFC 8098 report (`message.Receipt`: `multipart/report`, `Disposition: manual-action/MDN-sent-manually; displayed`), sent with `engine.SendReceipt`, which keeps no copy in Sent. It is sent from the account's address rather than the null sender RFC 8098 suggests, as submission servers often refuse one. Its errors go to the status bar.
    * An image put in an HTML message goes inline, as other clients do: a part of a `multipart/related` with the HTML, which shows it as `cid:ID`, no wider than 600 pixels. Images taken out of the text again are not sent. A draft continued, a reply or a forward keeps the images the message shows.

## Accounts

* Autoconfig (Look Up Settings), as other clients do, in `internal/autoconfig`: `autoconfig.<domain>`, `<domain>/.well-known/autoconfig`, the ISPDB (the public database of mail providers, whose address in the code is the one place its host is named), the ISPDB for the domain of the MX host, and RFC 6186 SRV records. All are asked at once; the most trusted answer wins.
* Name, email address, reply-to address, signature: text written in the dialog, or a file of text or HTML (`.html`, `.htm`) chosen instead (`signatureFile`), read each time a message is written so that changes to it are seen (`message.LoadSignature`). Of an HTML file only what is within the body is taken; in a message written as text it is turned into text; the images it shows from files on this computer are read and go with the message (`cid:`), as images put in it do, rather than as `file:` links no one else can see. A file that cannot be read is said so in the compose window, which is written without a signature, and refused by the dialog. A new message, or a reply above or below the quote, starts on an empty line with more below it before the signature (`writingLines`, three), as text or HTML; in HTML they are put in as plain blocks (`writingHTML`, `<div><br></div>`, the cursor put in the first by the element marked `cursorMark`), so that they take nothing of a quote, list or signature beside them.
* Server type: IMAP.
* Server name, port, username, password.
* Security settings
    * Connection: None, STARTTLS, SSL/TLS.
    * Auth: Normal password (SASL PLAIN, or LOGIN), Encrypted password (CRAM-MD5), TLS certificate (client cert + SASL EXTERNAL).
* Settings
    * Check for new messages on start (the inbox).
    * Load remote images when a message is shown (`loadRemoteImages`), rather than only when Load Remote Images is pressed.
    * Folders for operations (Sent, Drafts, Trash, Archive), chosen from the server's folders ("Read Folders from Server" lists them), or Automatic. Stick to the standards: Automatic uses the folder the server marks with the RFC 6154 special-use attribute (`\Sent`, `\Drafts`, `\Trash`, `\Archive`) first, then a usual name (Archive or Archives, Sent Items, Deleted Items, ...), at any level (as INBOX.Archive). If there is none, it is made on the server the first time it is needed (`engine.ensureFolder`, which lists the folders again first, so that one is never made beside a folder that is there but was not known of, as when mail is sent before the folders were ever listed: `TestFolderFoundBeforeMade`), as Sent, Drafts, Trash or Archive, in the personal namespace (NAMESPACE, as INBOX. on some servers), and marked with its use where the server supports CREATE-SPECIAL-USE. Creating a folder is not destructive and needs no confirmation: neither does New Folder… on an account's menu in the side bar (`engine.CreateFolder`), which makes one among the user's own folders or within another.
    * Archive divides archived mail as other clients do, by when each message was sent: by default into a folder for each year within the archive (`Archive/2026`), or one for each month (`Archive/2026/2026-03`), or not at all, as the account says ("Archive into" on the Folders tab). The folders within are made as they are needed, with the server's delimiter; a server without folders within folders keeps everything in the archive itself. Mail already in the archive, or a folder within it, is not archived again.
    * Compose as text or HTML, and quote position (reply above or below the quote).
    * Outgoing server (SMTP): description, server, port, username, password, connection and auth settings, and a Test Connection button (the incoming server has one too).

## Code layout

* `main.go`: finds the settings and data folders, starts Qt.
* `internal/appicon`: the program's icon (`appicon.png`), embedded.
* `internal/icons`: every other icon, drawn for the program as SVG (`svg/<name>.svg`) and embedded; `internal/ui/icons.go` draws them with Qt SVG. They are all in one outline style, which a test checks: a 24 grid, `fill="none"`, `stroke="currentColor"` 1.5 wide with round caps and joins, set only on the root, and nothing filled but in `currentColor` (small dots). They are drawn by an icon engine of our own (`newIconEngine`) each time they are shown, with `currentColor` the palette's colour of text (of disabled text where disabled, of selected text where selected), so they follow a change of theme with nothing made again. The side bar's are tinted instead (`sidebarTints` in `foldertree.go`, through `tintedIcon`): a colour for each kind of folder, one for a light theme and one for a dark (chosen by the lightness of the text), with the shapes filled by a pale wash of it (`fillOpacity`, drawn first from the same SVG with its root's `fill` set and its outline taken off, so that no fill covers an outline), and a selected folder in that of selected text, as the colour would not show on the selection. Qt's own pixmap of an engine is not cleared, so the engine makes its own on a transparent image. No icon comes from the desktop's theme or the style: draw a new one in the same style.
* `internal/settings`: the settings file and the data folder.
* `internal/crypt`, `internal/jsonfile`, `internal/homedir`: encryption with SSH keys via age, encrypted files written atomically with 0600 permissions, and `~` paths.
* `internal/account`: accounts and their encrypted files.
* `internal/addressbook`: the address book and its encrypted file.
* `internal/store`: the encrypted local cache (folders, indexes, messages, outbox).
* `internal/remote`: IMAP (go-imap v2), with the safety rules above. `conn_test.go` tests the connection itself (logging in, appending, `Check`, `Abort`, idling in `Watch`). `remotetest` is the in-memory server for tests, and `condstoretest` an IMAP server for tests that has CONDSTORE.
* `internal/send`: SMTP (go-smtp). `sendtest` is an SMTP server for tests, which records what it is given (envelope, DSN options, data), and takes mail only from a client logged in once told who (`Server.Login`, by PLAIN or LOGIN).
* `internal/message`: parsing for display (go-message, any charset), building outgoing mail, reply and forward helpers.
* `internal/autoconfig`: looking up server settings.
* `internal/images`: fetching the images a message links to on the web, when the user asks.
* `internal/engine`: the per-account workers that keep the cache in step and run operations: `engine.go` (the engine, its workers and status), `index.go` (indexes and saving them), `sync.go` (synchronising and IDLE), `syncall.go` (Synchronise All Folders, unread counts), `messages.go` (opening, flagging, moving, archiving, deleting), `outgoing.go` (sending, drafts, the outbox), `special.go` (the Sent, Drafts, Trash and Archive folders), `folders.go` (making and deleting folders).
* `internal/instance`: keeping to one copy of the program running, and handing over to it.
* `internal/desktop`: the desktop entry and icon, written to `~/.local/share/applications` and `~/.local/share/icons` at every start (`desktop.Install`, from `main.go`), as triggerapi does, so the program can be started from the desktop's menus. It needs no Qt.
* `packaging`: what the AppImage is made with (`appimage.sh`, `AppRun`, `apemail.desktop`).
* `internal/ui`: the Qt interface. Tests run offscreen (`QT_QPA_PLATFORM=offscreen`). The compose window is `compose.go` (the window, sending, drafts, attachments, opening one to write, reply or forward), `composemenus.go` (the Edit menu), `composeimages.go` (pictures put in a message) and `composebody.go` (the signature, the quote and the room to write above them), and `editor.go` its body. `messageview.go` is the message shown, and `webview.go` Qt WebEngine, which shows its body, and what keeps it from the internet. `attachments.go` has the attachments of the message shown, and `flowlayout.go` the layout that wraps them. `folderdialog.go` has New Folder and Delete Folder, and `Window.sidebarMenu` the menus of the side bar.

## Building

* Run `make build` after every change, so that the `apemail` binary is always the code as it is.
* Nothing is built in the project's folder but the finished files, which are gitignored: `make build` puts only the `apemail` binary there, and `make appimage` (`packaging/appimage.sh`) builds in a folder of its own in `/tmp`, removed when it is done, and puts only the AppImage there. No `build` folder.
* Never run the AppImage workflow locally (in a container or otherwise): it runs on GitHub.
* `make build`, `make run`, `make test`, `make bench`, `make vet`, `make appimage`. Every target that runs tests gives them a timeout (`TEST_TIMEOUT`); so does every test run by hand, benchmarks and single tests included (`go test -timeout 5m ...`).
* Releases are made by the GitHub workflow `.github/workflows/appimage.yml`, when a `v` tag is pushed or by hand from the Actions tab: on Ubuntu 24.04, whose glibc (2.39) is the oldest the AppImage then runs on, with Qt's own build of Qt 6.12 (installed by aqtinstall into `/opt/qt`, and kept from one run to the next), as qute builds with nothing older and Ubuntu's Qt is 6.4. Qt WebEngine and the modules it uses (Qt WebChannel, Qt Positioning) are asked for by name, and the script checks that it and its `QtWebEngineProcess` are in the AppImage (`packaging/appimage.sh`). The script gives the bundling tool a copy of Qt's plugins with only Qt's own (`lib*.so`, not the desktop's) and none of Qt Positioning's (the `position` folder, which the tool only warns is not there): one of those needs Qt SerialPort, which is not installed, and stopped the workflow, and mail has no use for where the computer is. Do not install Qt SerialPort to bring them back. It is triggerapi's workflow, with Qt WebEngine. Keep `QT_VERSION` no older than the Qt qute is made from.
* `make screenshot` draws the window into `docs/screenshot.png` (`TestScreenshot` in `internal/ui/screenshot_test.go`): a sample mailbox on the in-memory server, at 1280×800. Run it again whenever what the window looks like changes.
* The icon (a gorilla's face) is `internal/appicon/appicon.png`, a 256×256 PNG embedded by the `appicon` package, so the program needs nothing beside its binary. Replace the file to change it, with one of the same size (the desktop installs it as a 256×256 icon, and a test checks). The desktop entry names the icon by a path that does not change, so a desktop that has the old one cached (KDE keeps `~/.cache/icon-cache.kcache`) shows it until that cache is cleared or the session restarts; the window's own icon is the new one at once.
